# Chores

Running log of simple fixes and refactors (no spec or behavior change). `- [ ] <what and why>` → `- [x]` when applied.
- [x] floor_plan: lock the room's direction only once there is enough wall (200 cells or 3 m fitted); it locked on the first 6-cell map, so an early short wall tilted every wall for the run. Regression test `test_tiny_early_map_does_not_lock_direction`.
- [x] Target labels never resolved: `name_and_id` looked profiles up by the published detector label (`can`), but `load_class_profiles` keys them by `canonical_class` (`soda can`), so every lookup missed and every target showed its raw label. The bridge now joins the two through each profile's `detector_labels`, and a profile with no `display_name` falls back to its `canonical_class` rather than the raw label. `class_profile_path` also defaults to `dome_vision_ros`'s installed `class_profiles.yaml` — the robot's own vision config, so the viewer cannot drift from what the camera image is labelled with. Proven against `f36run6`: `soda can · CN1`, `coffee cup · CP23`. Three new tests.
- [ ] static/app.js is 580 lines and panels.js 416, both over the style guide's ~300-line smell. app.js is the one to split: the floor raster and the draw* routines are a coherent half that could become map_draw.js. Not urgent, and not worth doing while F02 is about to change the view transform.
- [x] app.js: laser rays were too faint to read at `globalAlpha` 0.13; raised to 0.22 (user's call, 2026-11-15). Hit dots left at 0.6.
- [x] CLAUDE.md: the documented `rosdep install --from-paths src/dome_viz -y` cannot work — `package.xml` depends on `dome_semantic_msgs`, `dome_telemetry_msgs` and `dome_semantic`, which are workspace source packages, so rosdep tries to resolve them as apt keys and fails. Corrected to name all four paths with `--ignore-src`.
- [x] Bag replay drew no robot: the launchfile's `use_sim_time` argument collides with `better_launch`'s own switch and was never populated, and that switch alone set nothing on the node either. The launchfile now declares `sim_time` and passes it through `params`; `make replay` uses `--sim_time True`. Verified on `viz01`: robot, trail and laser all flow. `test_launch.py` guards the name and the wiring.
- [x] Makefile: `make stop` kills the bridge, the launchfile and any bag replay, and reports whether 8080 is free. The pkill patterns are bracketed so they cannot match the recipe's own shell.
- [x] panels.js: "last heard" on the not-connected status line took `Math.max` of the source ages, so it reported the source heard from *longest* ago (e.g. a camera closed minutes earlier) rather than when the robot last spoke. Now `newestAge`, `Math.min`, matching `view_state.is_connected`'s `any(...)` over ages. Manual regression check (the page has no JS tests by decision, TF01.7/TF01.8), **on the live robot at TF01.12**, because a replay can never leave "live" (I02, face 3): open the camera panel, close it, then stop the robot's stack; the line must read seconds since the stack stopped, counting up, not the camera's older age. **Not yet run.**
- [x] app.js: dragging the map deselected the selected object, because a drag ends in a `click` on the stage, which the empty-map handler read as a deselect. `pointermove` now sets `hasDragged` and the click handler ignores the click that ends a drag. Manual regression check: select an object, drag the map, release — the selection and detail block stay; a plain click on empty map still deselects.
- [x] bridge_node: the laser lagged far behind the robot because ~96 % of scans were dropped. `take_scan` looked up `map -> laser` at the scan's own stamp, which is ~45 ms newer than the newest transform, so `ExtrapolationException` (measured on `viz01`: 24 of 647 resolved). A timeout cannot help, since the TF listener shares the single-threaded executor. Now the newest scan is held as pending and retried on the 10 Hz pose timer. Regression test `test_a_scan_ahead_of_tf_is_sent_once_tf_catches_up`. User confirmed on a `viz01` replay, 2026-11-16: the rays keep up.
- [x] app.css: object class colours were never defined. `panels.js` colours markers with `var(--can)` / `var(--cup)`, which the approved mockup defines (`mockup/index.html:21`) but `app.css` did not, so pins had no fill and chips no class border. Copied the mockup's values into all three colour blocks. Manual regression check: on a replay with targets, cans show orange and cups purple, on the map and in the Key, in both themes.
- [x] Makefile: `make view` and `make replay` say which clock they use, and refuse the mix-ups that silently draw no robot — `view` while a bag publishes `/clock`, `replay` with no or a missing `BAG`, or while a viewer or bag already runs (I02). Twice on 2026-11-16 the wrong pairing hid the robot.
- [ ] bridge_node: warn once when a TF lookup is rejected as hours or days stale, which almost always means a wall-time viewer is reading a bag's (or a remote replay's) transforms. On 2026-11-16 a bag played from another machine after `make view` had started, so the startup guard never saw `/clock`, and the robot silently never appeared. Needs a regression test.
